# Referee report: Paper2Agent (arXiv v1)

## Summary and overall assessment

Paper2Agent takes a computational paper and its codebase, turns selected workflows into callable tools, and connects them to a conversational agent through the Model Context Protocol (MCP). To show that this makes papers reliably reusable, the conversion must preserve the methods a reader needs, and the agent must use them correctly on questions other than those used to build it.

The authors report 22 AlphaGenome tools built without human intervention in around three hours on a personal laptop, six TISSUE tools, and seven Scanpy preprocessing and clustering tools built in around 45 minutes. The AlphaGenome agent matched the reference answers on **15/15 tutorial queries and 15/15 author-curated new queries**. The TISSUE example compares prediction intervals for *Acta2* against a manual analysis on mouse cortex data; the Scanpy example compares workflows on three 10x PBMC datasets not in its codebase (Results, Figs. 2–4; Extended Methods).

**Soundness: MAJOR_REVISION.** The examples support a useful feasibility claim: a generated interface can do more than explain a method; it can run the original software and return its outputs. They partly support the broader claims about reliable conversion, transfer and easier reuse. I would give most weight to four things: a record of what survived conversion, a clear separation of tutorial replay from transfer, quantitative agreement for the two multistep pipelines, and a comparison that isolates what the generated interface contributes. None of these reservations implies that the reported numerical answers are wrong.

## Strengths

The most persuasive design choice is to compare answers to execution of the original scientific software, rather than judging whether a reply sounds plausible. For the new AlphaGenome inputs, the authors explicitly checked the expected numerical values by hand-running that code (Fig. 2C). In TISSUE, the natural-language request reaches from count matrices through imputation to uncertainty estimation, not just to a documentation excerpt (Fig. 3C). Scanpy makes a different point: the generated prompt records the order of analysis and instructs the agent to inspect the data before choosing parameters (Fig. 4B; Extended Methods). Together these examples give tools, data resources and workflow prompts distinct scientific purposes. Source references in the wrappers also give a reader a route back to the implementation.

## Major concerns and concrete requests

1. **What fraction of the intended method reached the server?** The Extended Methods state, “If functions repeatedly fail, their MCP decorators are removed”. That is a sensible safeguard. It also means 22 exposed AlphaGenome tools cannot tell us whether all intended features worked on the first pass or whether difficult features were dropped. I found no evidence that a particular function *was* dropped in these builds. Please use the recorded logs to reconcile, for each case, the tutorials considered, features selected or left out, functions attempted, retries, removals and reasons, human interventions, and final tools. Keep the intentionally limited scope of Scanpy separate from failed implementations. If the logs cannot establish completeness, report the retained capabilities rather than “comprehensively covering” the method.

2. **Which new questions require a new operation?** The testing agent “uses only the tutorial’s own examples” (Extended Methods). The first 15 AlphaGenome questions therefore test tutorial fidelity. The second 15 are a genuine improvement: the authors changed, among other things, variant positions and tissue contexts. Yet a new input to an existing score-and-read operation tests something different from deciding which operations to combine. For Fig. 2C, map each query to its nearest build example, identify what changed in the input, operation or workflow, and state when the tools and questions were fixed relative to one another. Limit the transfer claim to the variation actually tested. To retain a broader claim, use independently specified questions on frozen tools, with expected outcomes for new task compositions and for a request the agent should decline.

3. **How closely did the multistep outputs agree?** In TISSUE, “The output matches the results obtained by human experts running the pipeline manually.” In Scanpy, the Extended Methods describe outputs as “consistent with human-executed analyses.” The manual pipelines are appropriate references. But reproducing the order of operations, a plot that looks similar, and the same scientific result are three different achievements. Please compare the saved outputs per dataset, giving reference settings, seed handling, acceptance tolerances and observed differences. For TISSUE, pair the requested records and compare both interval endpoints. For Scanpy, report agreement on which cells survived and on cluster membership without depending on cluster names. That table would let a reader decide whether the differences matter, even if the outputs are not identical.

4. **What does the generated interface add to the coding agent?** “We use Claude Code as the downstream AI agent in our case studies” (Results, Overview). A human running the package supplies a reference answer, not a comparison with what Claude Code could do using the repository and tutorials directly. The strongest competing explanation is that good example code, an installed environment and a capable base agent suffice for these tasks. Compare the same model with and without the generated MCP, using the same working environment, source materials, data, queries, credentials where needed, and effort budget. Report paired differences in correct completion and effort, including interventions. If this comparison is outside the paper's scope, present the results as a demonstration of the combination, not evidence that the interface itself improved performance or reduced effort.

5. **Which papers does the procedure apply to?** The Introduction says “any research paper can be converted into an agent”. The Discussion is more convincing: it acknowledges incomplete code and reserves other kinds of research output for future work. The three cases concern related computational biology methods with code, tutorials and outputs against which wrappers can be tested. Bring this qualification into the abstract and introduction, say how the cases were chosen, and distinguish tested prerequisites and the one tested client from proposed extensions. A new field-wide survey is not necessary to support the narrower paper.

## Minor comments and questions

6. **Interpret the perfect scores as counts.** For the “15 original tutorial examples and 15 novel queries” (Extended Methods), give first-attempt successes, independent sessions and retry allowances by query; identify any unmeasured run-to-run variation. A binomial interval treating author-curated queries as independent random draws would not, by itself, quantify performance for future users. Separate uncertainty across runs from uncertainty across kinds of task. This clarifies the scope of the two observed fractions rather than disputing them.

7. **Distinguish accessibility from adoption.** “Users only need to provide the data path” is informative about the Scanpy interface (Fig. 4); “eliminating the need for programming expertise” is an inference about users (Results, Overview). Describe reduced coding as an interface feature and usability as a proposed benefit unless task completion and needed assistance have actually been measured in the intended user group.

8. **Keep SORT1 as an alternative hypothesis.** The LDL example (Fig. 2D) reports a liver quantile score of 0.99982 for SORT1 versus 0.99998 each for CELSR2 and PSRC1. The manual GTEx lookup supports associations with all three. SORT1’s known biology can reasonably change an investigator’s priority; it does not turn the same AlphaGenome predictor into “independent model-based evidence”. Set the three candidates side by side, distinguish the model output, biological rationale and human lookup, and describe the result as reprioritization, not causal validation. The manuscript's own caution about multi-gene loci supports that reading.

9. **Clarify the remote service’s trust boundary.** The Extended Methods show a credential placeholder inside a user prompt and describe “basic security defaults”. No actual disclosure is shown. For the hosted configuration, say which components receive data and credentials, who can access them, what is retained or redacted, and which datasets are suitable. Show a protected configuration route for credentials instead of instructing users to put live keys in conversation. This is a request for deployment guidance, not a claim that an incident occurred.

10. **Identify the evaluated release.** The Methods say to “pin dependencies”. Please identify the immutable release or manifest that ties paper and server versions, backend identifiers and dates, prompts, wrappers, environment locks, reference outputs and scored traces to the reported comparisons. State which hosted dependencies cannot be frozen. This is about locating the evaluated system, not assuming the linked code lacks these materials.

11. **Put build time in context.** “Around 3 hours on a personal laptop” for AlphaGenome is a useful wall-clock observation (Fig. 2 case study), not the total cost of using the service. For the two timed builds, identify laptop and remote-service configuration, what was metered, which costs recur per query, and what upstream changes require revalidation. Mark unmeasured costs as such; a full economic study is unnecessary.

## Code and data availability

The manuscript lists the Paper2Agent repository, three hosted MCP servers, an AlphaGenome agent, the three PBMC input files and the mouse cortex dataset. Extended Methods direct the reader to the repository for setup, prompts and detailed AlphaGenome queries. These are concrete pointers. I did not access the links or run the software in this manuscript-only review, so I cannot attest to their contents or present-day runnability. Request 10 concerns the link between those resources and the published results.

## Significance and venue fit

The distinctive contribution, on the paper's own account, is **automatic construction of a source-linked, callable interface from an existing method’s tutorials**, not a new biological model. The Introduction credits executable papers and Jupyter-backed publications for joining exposition and runnable code, Papers with Code for linking papers to repositories, and CellVoyager and Biomni as agents for biological analysis. Paper2Agent asks a different question: can the *interface itself* be generated from the authors’ implementation and reused? This comparison is based on the manuscript's descriptions, not an independent priority search. The work is promising for a computational methods or research software venue. A broader methods readership would have a stronger reason to adopt it if the generated interface, rather than just the underlying software and base agent, delivered a reproducible advantage on held-out workflows.

## Path to a stronger paper

**Must do, using existing material first:** lead with the two separate 15/15 results and their scope, account for the conversion attempts, and score the saved TISSUE and Scanpy results against their references (requests 1–3, 5). A paper demonstrating execution and measured fidelity in these three settings would stand on its own. **Highest-value additional comparison:** if the authors want to claim an advantage for Paper2Agent, run the matched direct-repository control in request 4 on the held-out task families in request 2. Otherwise narrow the attribution. Closing these five major points would resolve the basis for my recommendation; the remaining requests are reporting improvements, not demands for a larger experiment.
